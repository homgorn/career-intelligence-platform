# AGENTS.md — Career Intelligence / AI Profession Intelligence

Этот файл IDE читает автоматически. Здесь — только правила и указатели.
Спецификации лежат в `career-intelligence-research-specs-v02/` и только на чтение.

## 0. Суть проекта

Продукт улучшает измеримые карьерные и рабочие исходы человека.
AI — одно из средств. Рекомендация без AI валидна, если она даёт больше ценности,
меньше риска или меньше стоимости внедрения.

Центральный цикл:

```
USER/ORG → CONTEXT → GOAL → TASK/WORKFLOW → DIAGNOSIS
→ OPTIONS (AI / NON_AI / HUMAN) → IMPLEMENTATION → VERIFICATION
→ MEASURED OUTCOME → FEEDBACK → UPDATED RECOMMENDATION
```

Центральная сущность продукта — **WorkRecipe**.
Ключевая метрика — измеримый исход для пользователя, а не количество
рекомендаций, промптов, AI-вызовов или времени в приложении.

## 1. Несущие принципы

1. Customer outcome > AI feature.
2. Evidence > assumption.
3. Deterministic policy > LLM judgment.
4. Authoritative DB > derived index > LLM memory.
5. Provenance обязателен для всех consequential recommendations.
6. Security / privacy / legal gates не обходятся ради скорости.
7. Внешние провайдеры — адаптеры, а не зависимости домена.
8. Никаких секретов в контексте модели.
9. Агент не получает больше полномочий, чем требует задача.
10. Необратимые / высокоимпактные действия требуют подтверждения человеком.
11. Каждая значимая фича измеряется.
12. Каждая production-фича имеет rollback.
13. У каждой рекомендации есть метод верификации.
14. У каждого инструмента есть lifecycle и владелец.
15. У каждой значимой связи данных есть provenance.
16. Любое изменение, затрагивающее контракты, требует ADR.
17. Не строить P1/P2 до прохождения соответствующего gate.
18. Не добавлять сложность только потому, что она есть в спецификации.
19. Не выдумывать отсутствующие требования.
20. При неопределённости — остановись и запиши OPEN QUESTION.
21. Один этап за сеанс. Без HARD STOP следующий этап не начинается.
22. Архив спецификаций — read-only. Не копировать, не править, не переименовывать.

## 2. Как работать

В проекте есть скиллы этапов (`ci-stage-*`, см. `skills/README.md`).
Они подключаются автоматически, когда человек называет этап или задачу,
и ведут на карточку `docs/ops/stages/STAGE-XX-*.md`.

Перед отчётом о завершении этапа запусти `python tools/check.py` —
это единственное определение «зелёного» (CI вызывает ту же команду).

1. Прочитай `docs/ops/RUNBOOK.md` — реестр этапов и порядок.
2. Получи от человека имя этапа или `TASK-ID`.
3. Прочитай карточку этапа в `docs/ops/stages/STAGE-XX-*.md`.
4. Прочитай входные артефакты и только те спеки, которые указаны в карточке.
5. Выполни этап, создай выходные артефакты.
6. Заполни `docs/ops/STAGE-STATUS.md`.
7. Остановись. Жди команду человека.

Никогда не запускай два этапа подряд, даже если «всё готово».

## 3. Дисциплина чтения

- `career-intelligence-research-specs-v02/` — единственный источник спецификаций,
  только на чтение. Актуальный состав и статусы — `docs/specs/SPEC_INDEX.md`,
  полные хэши — `docs/specs/SPEC_INDEX_DATA.tsv`.
- Файл `old specs не трогать пока.7z` не распаковывать и не читать.
- Не копируй архив в `docs/specs`. Только ссылки и хэши.
- Не перечитывай все 109 файлов каждый раз. Читай только то, что указано
  в `spec_refs` карточки этапа или задачи.
- Спеки — это оглавления, а не детальные спецификации. Молчаливое дополнение
  типов, кардинальностей и инвариантов запрещено: сначала предложи контракт
  на утверждение, потом код.

## 4. Язык и именование

- Идентификаторы, имена событий, поля API и БД, значения enum — по-английски
  ровно так, как в архиве: `WorkRecipe`, `NON_AI`, `recommendation.generated`,
  `OUTCOME_MEASURED`, `policy.blocked`.
- Нарративные документы — на русском. При первом упоминании термина в скобках
  указывай английский канон: «рецепт работы (`WorkRecipe`)».
- Тесты и комментарии к коду — на языке команды, комментарии допустимы на русском.
- Словарь терминов — `docs/architecture/GLOSSARY.md`.

## 5. Гейты

Три уровня, не путать:

| Уровень | Когда | Кто проводит | Артефакт |
| --- | --- | --- | --- |
| Stage gate | после каждого этапа | IDE проверяет, человек подтверждает | `docs/gates/STAGE-GATE-XX.md` |
| Release gate | граница P0 / P1 / P2 | человек решает, IDE готовит доказательства | `docs/gates/RELEASE-GATE-P0.md` |
| Production gate | перед выпуском в продуктив | человек + внешний аудит при необходимости | `docs/gates/PRODUCTION-GATE.md` |

Release gate не проходит по факту готовности бэклога — только по доказательству
повторяемой ценности и приемлемой экономики.

## 6. Если спецификация молчит

Правильное действие — не догадка, а явное решение:

1. Запиши вопрос в `OPEN QUESTIONS` выходного артефакта.
2. Предложи варианты ответа с ценой каждого.
3. Если вопрос влияет на контракт — предложи изменение контракта через ADR
   и не начинай код до утверждения.
4. Если вопрос блокирует этап — пометь этап `BLOCKED_ON_QUESTION` в
   `docs/ops/STAGE-STATUS.md` и остановись.

## 7. Чего не делать никогда

- Не отдавать LLM решения по security, legal, billing, entitlement, safety.
- Не хранить секреты, ключи, пароли в записях БД, логах, событиях и контексте модели.
- Не писать бизнес-правило внутрь промпта.
- Не делать vendor SDK зависимостью доменного слоя.
- Не считать векторный индекс или память модели источником истины.
- Не перезаписывать исторические данные и evidence молча.
- Не запускать P1/P2 до прохождения gate.
- Не оценивать готовность по наличию функций — только по доказательству исхода.
