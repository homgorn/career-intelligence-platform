## Какую задачу решает репозиторий

Большинство AI-продуктов в карьерной сфере оптимизируют использование AI:
больше промптов, больше рекомендаций, длиннее отчёт, больше времени в
приложении. Этот проект оптимизирует **измеримый исход для клиента**: человек
выполняет реальную задачу, внедряет вмешательство, проверяет результат, и
исход фиксируется.

Один этот принцип меняет всё остальное:

| Принцип | Следствие в репозитории |
| --- | --- |
| Исход для клиента > AI-фича | Рекомендация без AI — полноценный результат первого класса |
| Evidence > предположение | У каждой рекомендации сохранена цепочка доказательств |
| Детерминированная политика > суждение LLM | LLM предлагает, решают типизированные сервисы |
| Authoritative DB > производный индекс > память LLM | Search, vector и graph — перестраиваемые проекции |
| Provenance обязателен | Утверждения хранят источник, дату, географию, уверенность, версию |
| Необратимые действия требуют подтверждения | Ни один агент не выполняет значимые шаги без человека |

Центральный цикл ценности, одинаковый на всех слоях архитектуры:

```
USER/ORG → CONTEXT → GOAL → TASK/WORKFLOW → DIAGNOSIS
→ OPTIONS (AI / NON_AI / HUMAN) → IMPLEMENTATION → VERIFICATION
→ MEASURED OUTCOME → FEEDBACK → UPDATED RECOMMENDATION
```

Центральная единица ценности — **WorkRecipe** (`WorkRecipe`): переиспользуемый
рецепт с доказательной базой, который связывает реальную задачу человека с
практическим вмешательством и измеренным результатом.

## Быстрый старт

```bash
git clone https://github.com/homgorn/career-intelligence-platform.git
cd career-intelligence-platform

python tools/runbook_validate.py            # проверить все задекларированные артефакты
python tools/runbook_validate.py --stage STAGE-00
python tools/runbook_next.py                # какая задача следующая и почему
python tools/gen_spec_index.py              # перегенерировать индекс спецификаций
```

Одна команда «всё локально»:

```bash
python tools/check.py            # JSON/CSV, ruff, формат, тесты,
                                 # diff индекса, stage-гейты, селектор
python tools/check.py --quick    # пропустить перегенерацию индекса и STAGE-00
python tools/check.py --json
```

Или по отдельности, как в CI:

```bash
pip install ruff pytest
ruff check tools
ruff format --check tools
pytest tools/tests
```

## Как устроено исполнение

Работа идёт по этапам. У каждого этапа есть триггер, объявленные входы,
объявленные выходы, Definition of Done, жёсткая остановка и путь отката.

```
STAGE-00 аудит → STAGE-00A пилот → STAGE-01 readiness → STAGE-02 контракты
  → STAGE-03 foundation → STAGE-04 домен/данные → STAGE-05 рекомендации
  → STAGE-05A гейт LLM → [STAGE-06 LLM/RAG, условно]
  → STAGE-08 сайт → STAGE-08A дистрибуция → STAGE-09 security/legal
  → STAGE-10 аналитика → STAGE-11 вертикальный срез → STAGE-12 P0 gate
  → STAGE-13/14 (цикл задач) → STAGE-15 health check → STAGE-16..19
```

Три правила делают процесс надёжным:

1. **Один этап за сеанс.** Этап заканчивается жёсткой остановкой и ждёт человека.
2. **Решения человека остаются за человеком.** Выбор пилота, необходимость LLM
   и release-гейты не автоматизируются. Инструменты сообщают `WAIT`, а не
   молча проходят.
3. **Definition of Done частично исполняем.** Декларации описывают, что этап
   обязан произвести; валидатор выполняет их и роняет сборку.

LLM-слой условен по замыслу: `STAGE-05A` требует письменного обоснования до
начала любой работы с LLM и RAG, потому что `NON_AI` — легитимный исход, а
model inference стоит последним в иерархии evidence.

## P0 scope и гейт ценности

P0 доказывает **один полный цикл ценности для одного конкретного workflow**.
Всё остальное явно отложено — см. `docs/architecture/P0_SCOPE.md`.

В P0 входят: мультиарендантный фундамент, аутентификация и изоляция, срез
таксономии пилотной профессии, `WorkRecipe`, детерминированный движок
рекомендаций с policy gates, один полный вертикальный срез в трёх режимах
(сделаю сам / проведи меня / помоги сделать), фиксация исхода, аналитика по
замороженному каталогу событий и минимальный канал дистрибуции.

В P0 **не** входят: адаптивный quiz, загрузка резюме, job matching, движок
карьерных переходов, реестр инструментов и MCP, learning paths, B2B, партнёрские
программы, масштабное SEO, сложный billing, knowledge graph, agent runtime,
маркетплейс.

Гейт P0 сравнивает измеренные значения с порогами, которые владелец задаёт
**до** начала работы в `docs/architecture/PILOT_DECISION.md`:

| Показатель | Референсный порог |
| --- | --- |
| Реальные пользователи, прошедшие цикл | ≥ 20, не сотрудники и не друзья |
| Time to first value | ≤ 15 минут (медиана) |
| Завершили хотя бы одно действие из WorkRecipe | ≥ 30% |
| Вернулись записать исход за 14 дней | ≥ 10% |
| Нерешённые блокеры security / privacy | 0 |
| Рекомендации с provenance и версией политики | 100% |
| Cost per verified outcome | не выше цели, заданной при пилоте |

`PASS` требует выполнения всех порогов. `CONDITIONAL_PASS` допускает один.
`FAIL`, если исход не доказан или открыт юридический/security блокер.
Непройденный гейт не открывает P1.

## Текущий статус

| Этап | Статус |
| --- | --- |
| `STAGE-00` аудит | Завершён — 109 файлов инвентаризированы, зафиксировано 8 конфликтов архива |
| `STAGE-00A` решение по пилоту | Ждёт владельца: ICP, профессия, workflow, страна, пороги |
| `STAGE-01`…`STAGE-19` | Не начаты |

Следующий этап требует человеческого решения и не автоматизируется. Селектор
сообщает об этом прямо:

```
=== Селектор следующей задачи ===
Пилот подписан: НЕТ (нет docs/architecture/PILOT_DECISION.md)
Gate: P0=None P1=None P2=None
Разрешённые приоритеты: P0

[BLOCKED] BLOCKED_ON_PILOT: нет docs/architecture/PILOT_DECISION.md
```
