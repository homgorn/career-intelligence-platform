# ASSERTIONS — машиночитаемые проверки этапов

Каталог `docs/ops/assertions/*.json` — это декларация того, что значит
«этап выполнен». Валидатор `tools/runbook_validate.py` читает эти файлы
и проверяет артефакты. Код и проверка разделены: чтобы добавить этап или
проверку, не нужно менять Python.

## Схема файла

```json
{
  "stage": "STAGE-XX",
  "depends_on": ["STAGE-YY"],
  "inputs": ["путь к входному артефакту или каталогу"],
  "outputs": ["путь к обязательному выходному файлу"],
  "checks": [
    {"kind": "file_exists", "path": "docs/....md"},
    {"kind": "nonempty_field", "path": "docs/tasks/MASTER_BACKLOG.json", "pointer": "tasks[*].customer_value"}
  ]
}
```

Файл `ALWAYS.json` описывает инварианты проекта: он проверяется всегда,
на любом этапе и в CI.

## Виды проверок

| kind | Что проверяет |
| --- | --- |
| `file_exists` | файл существует |
| `dir_exists` | каталог существует |
| `json_valid` | JSON парсится |
| `tsv_rows_min` | в TSV не меньше N строк |
| `nonempty_field` | ни одно значение по pointer'у не пустое |
| `deps_exist` | все depends_on есть в бэклоге |
| `deps_acyclic` | граф зависимостей без циклов |
| `archive_hashes` | sha256 архива совпадает с SPEC_INDEX_DATA.tsv |
| `spec_index_mentions_all` | SPEC_INDEX.md упоминает каждый файл архива |
| `terms_present` | документ содержит перечисленные термины |
| `sections_present` | документ содержит перечисленные заголовки |
| `canonical_events` | каталог событий содержит все 17 канонических событий |
| `human_signed` | документ подписан человеком (`signed_by`) |
| `gate_status` | в gate-отчёте есть `STATUS:` |
| `next_task_single` | в NEXT_TASK.md ровно одна задача |
| `stage_registry_consistent` | каждый этап реестра имеет карточку с обязательными разделами; нет карточек вне реестра |
| `skills_cover_stages` | каждый этап имеет скилл, `name` в frontmatter совпадает с папкой |
| `assertions_cover_stages` | каждый этап реестра имеет декларацию проверок |
| `markdown_links_resolve` | относительные ссылки в документации указывают на существующие файлы |
| `min_occurrences` | шаблон встречается не меньше N раз (содержательная полнота артефакта) |
| `frontmatter_equals` | поле YAML-frontmatter равно ожидаемому (например, статус ADR) |

## Статусы

| Статус | Смысл |
| --- | --- |
| `PASS` | проверка пройдена |
| `FAIL` | проверка не пройдена, код возврата 1 |
| `WAIT` | нужна подпись или решение человека; не FAIL, но этап не закрыт |
| `SKIP` | неизвестный вид проверки, требует внимания автора декларации |

Режим `--strict` считает `WAIT` за `FAIL`.

## Что валидатор НЕ проверяет

- качество кода и прохождение тестов продукта;
- правильность архитектурных решений;
- истинность утверждений в документах;
- соответствие кода контрактам — только наличие и структуру контрактов.

Это осознанное ограничение: валидатор проверяет артефакты, а не заменяет
инженерную работу.

## Команды

```bash
python tools/runbook_validate.py --list
python tools/runbook_validate.py --stage STAGE-00
python tools/runbook_validate.py --prereq --stage STAGE-04
python tools/runbook_next.py
python tools/runbook_next.py --json
```

## Как добавить проверку

1. Выберите существующий `kind` или добавьте новый в `CHECKS`
   в `tools/runbook_validate.py`.
2. Добавьте запись в `checks` соответствующего файла декларации.
3. Прогоните валидатор и убедитесь, что проверка падает на отсутствующем
   артефакте и проходит на присутствующем.

Не добавляйте проверки, которые невозможно выполнить механически: они
превращают валидатор в фикцию.
