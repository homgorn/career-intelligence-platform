# tasks — единый бэклог проекта

Здесь живёт **один** живой бэклог. Второго не бывает: расхождение двух графов
задач — типовая причина, по которой агент начинает противоречить сам себе.

## Файлы

| Файл | Назначение |
| --- | --- |
| `MASTER_BACKLOG.json` | единственный источник истины по задачам |
| `NEXT_TASK.md` | ровно одна следующая задача, выбранная механически |
| `P0/`, `P1/`, `P2/` | карточки задач по шаблону `docs/templates/TASK_CARD.md` |

## Правила

1. **ID не перезапускаются.** Идентификаторы взяты из
   `MASTER_DEPENDENCY_GRAPH.json` архива; новые задачи продолжают нумерацию
   (`TASK-P0-010`, …), а не начинают её заново.
2. **Каждая задача имеет `spec_refs`** — файл и раздел спеки. Задача без
   ссылки на спеку либо тривиальна, либо требует ADR.
3. **`customer_value` без измеримого критерия — невалидная задача.**
   Это проверяется на этапе STAGE-02 и далее.
4. **Зависимости только по ID** из этого бэклога.
5. **Статус меняет только исполнитель задачи**, не планировщик.
6. **`NEXT_TASK.md` обновляется после каждой выполненной задачи** этапом
   `STAGE-13`, а не «когда удобно».

## Статусы

`PENDING` · `IN_PROGRESS` · `BLOCKED_ON_PILOT` · `BLOCKED_ON_QUESTION` ·
`BLOCKED_BY_GATE` · `DONE` · `DEFERRED`

## Выбор следующей задачи

```bash
python tools/runbook_next.py          # текст
python tools/runbook_next.py --json   # для инструментов
```

Правила выбора: зависимости → P0 blockers → customer value → architecture
risk → cost. P1 закрыт до `RELEASE-GATE-P0.md` = `PASS`, P2 — до P1.

Особый случай: задача, помеченная `produces_pilot_decision`, не блокируется
отсутствием подписанного пилота — она сама его создаёт. Иначе проект
заблокирован навсегда.

## Что не делать

- Не добавлять задачи без customer value и Definition of Done.
- Не менять порядок зависимостей, чтобы «получилось побыстрее».
- Не начинать P1/P2 до соответствующего гейта.
- Не переносить сюда research-вопросы: для них `docs/research/`.
